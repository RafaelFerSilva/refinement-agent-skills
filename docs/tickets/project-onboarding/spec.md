# Spec: onboarding ongoing products and maintaining context across skills and chat prompts

Status: resolved
Origin: 2026-10-28 (commit 4a0a98f)

## Problem Statement

Teams adopting the package on greenfield products build domain context incrementally from their first meeting transcript or discovery session. Teams adopting it on ongoing (brownfield) products face a cold start, especially in `without-code` workspaces: when a Product Owner brings a standalone User Story from an advanced product into `/refine-story`, the workspace holds no glossary, no recorded architectural decisions, and no consolidated view of existing modules, rules, or integrations.

Because `requirements-rigor` and `socratic-examination` forbid silent invention, missing baseline context turns everything the team already treats as obvious into first-round questions or `[TO CONFIRM: whom]` markers. Users lack structured onboarding guidance explaining why this happens, where to place existing product documentation in the workspace, and how to turn legacy manuals, specifications, or code into reusable workspace context before refining stories.

A parallel gap affects teams running the standalone chat prompts on platforms with persistent memory or knowledge bases (such as Claude Projects, Custom GPTs, Gems, or Copilot Studio). Each examination session can resolve new domain glossary terms, surface architectural decisions, or establish product-wide rules, yet chat agents cannot write back to platform memory automatically. Emitting scattered glossary snippets mid-round leaves users with fragmented updates that are easy to miss at synthesis, while blindly emitting a full glossary replacement risks erasing pre-existing entries when the platform supplies knowledge files through partial retrieval rather than full-file injection.

## Solution

Provide a complete onboarding path for both greenfield and ongoing products across workspace skills and standalone chat prompts:

1. Introduce a user-invoked `/bootstrap-context` workflow skill that ingests existing product documentation, inspects product code in `with-code` mode, or conducts a structured onboarding examination when neither exists, curates ambiguous or conflicting legacy terms with the Product Owner via socratic examination, and publishes a clean domain glossary (`CONTEXT.md`), an auditable baseline overview of the current product (`product-overview`), optional architectural decision records, and stakeholder questionnaires for unresolved legacy gaps.
2. Extend `/configure-refinement` so workspace setup distinguishes greenfield from ongoing products, establishes where existing product reference material and the consolidated product overview live among workspace fact sources, and guides ongoing products to `/bootstrap-context` before their first story refinement.
3. Upgrade the chat-prompt adaptation layer so all examination workflows (`bootstrap-context`, `refine-story`, `requirements-discovery`, and `qa-plan`) deliver consolidated, copy-ready memory update blocks at final synthesis whenever a session adds or flags domain glossary entries, product overview facts, or architectural decisions, distinguishing safe full-file replacement from append-only deltas when platform memory may only be partially visible, and reminding the user in the final report to update their agent platform configuration.
4. Publish structured Getting Started guides in both `en-US` and `pt-BR` alongside updated repository entry points explaining target workspace anatomy, greenfield versus ongoing adoption playbooks, why rigor trades silent invention for explicit examination, and how to maintain context files in chat platform memory.

## User Stories

1. As a Product Owner joining an ongoing product in a `without-code` workspace, I want `/configure-refinement` to ask whether the product is new or already in production and show me where to place existing documentation, so that I know how to prepare the workspace before refining my first User Story.
2. As a Product Owner with legacy manuals, specifications, or exported stories, I want to run `/bootstrap-context` over those documents, so that the agent extracts domain roles, entities, active integrations, and active rules into reusable workspace context instead of re-asking baseline questions on every story.
3. As a Product Owner whose legacy documents contain conflicting synonyms or outdated rules, I want `/bootstrap-context` to challenge contradictions and ambiguities in socratic examination rounds with cited recommendations before writing context files, so that stale or contradictory terminology does not enter the glossary silently.
4. As an engineer or Product Owner in a `with-code` workspace for an ongoing product, I want `/bootstrap-context` to inspect the codebase via subagent alongside any available documentation before opening round 1, so that implemented roles, entities, constraints, and integrations become grounded recommendations citing source files while business definitions remain the Product Owner's decision.
5. As a Product Owner on an ongoing product with neither written documentation nor code access, I want `/bootstrap-context` to run a focused onboarding examination covering roles, core entities, production capabilities, and external integrations, so that I can seed baseline context from tacit team knowledge in one short session.
6. As a workflow consumer (`refine-story`, `qa-plan`, `requirements-discovery`, `meeting-minutes`), I want `CONTEXT.md` to remain strictly a domain glossary while operational baseline facts (modules, active integrations, cross-cutting rules, and current SLAs) live in a dedicated product overview document under the workspace documentation sources, so that glossary invariants hold without losing operational product memory.
7. As a stakeholder outside the refinement session, I want unresolved legacy or architectural questions surfaced during `/bootstrap-context` to be routed into recipient-specific questionnaires linked from the product overview artifact, so that open baseline gaps can be closed asynchronously.
8. As a user asking `/which-flow` how to start on an existing product or with a folder of legacy documentation, I want the router to direct me to `/configure-refinement` and `/bootstrap-context` before story workflows, so that I pick the right entry point without memorizing every skill.
9. As a chat-mode user maintaining `CONTEXT.md` and product overview documents in an AI platform's memory or knowledge base, I want every examination prompt (`bootstrap-context`, `refine-story`, `requirements-discovery`, `qa-plan`) to emit copy-ready memory update blocks at the end of synthesis whenever context changed in that session, so that I do not have to hunt through mid-round messages to update my agent configuration.
10. As a chat-mode user whose platform retrieves knowledge base files partially via search chunks, I want the prompt to emit a full replacement `CONTEXT.md` only when the complete glossary was pasted in the conversation or created from scratch and an append-only update block otherwise, so that updating platform memory never overwrites unseen glossary entries.
11. As a team member adopting the package in English or Brazilian Portuguese, I want a structured Getting Started guide in both `en-US` and `pt-BR`, so that Product Owners, QA engineers, and developers understand workspace layout, greenfield versus brownfield workflows, anti-invention guarantees, and chat-memory maintenance.
12. As a package maintainer, I want `/bootstrap-context` artifacts, localized vocabulary, prompt adaptations, and evaluation cases covered by the existing validation and grading harness, so that regressions in structure, language consistency, glossary safety, or prompt generation fail automated checks.

## Implementation Decisions

- **Preserve `CONTEXT.md` purity and introduce a separate product overview artifact:** `socratic-examination` restricts `CONTEXT.md` to domain glossary definitions (`Term` plus `_Avoid_`, no implementation details, scope decisions, or system state). `/bootstrap-context` therefore splits extracted knowledge across existing workspace boundaries: domain vocabulary enters `CONTEXT.md` (subject to the non-widening challenge pass and compatible with `diff-glossary`), genuine irreversible choices enter ADR files only when all three ADR criteria hold, and operational product baseline facts (purpose, roles summary, production modules/capabilities, active integrations, cross-cutting business rules and SLAs, open questions, and readiness status) are published to a dedicated product overview markdown artifact under workspace documentation (`docs/product-overview.md`), listed right after ADRs in the workspace fact-source priority order.
- **Keep setup and context ingestion as distinct user-invoked skills:** `/configure-refinement` remains a fast interactive configuration step (run once or when switching conventions) and gains project-stage inquiry (new versus ongoing product), guidance on placing raw legacy files under a reference documentation folder (`docs/reference/`), updated fact-source priority ordering in its template, and a concluding pointer to `/bootstrap-context` for ongoing products. `/bootstrap-context` is a standalone user-invoked workflow (`disable-model-invocation: true`, `allow_implicit_invocation: false`) so teams can gather legacy files after setup and re-run context ingestion later when new legacy modules enter scope.
- **Localized surface follows ADR 0004 and ADR 0005:** `/bootstrap-context` instructions and templates are authored canonically in `en-US` with explicit `pt-BR` localization at the point of use. Triage labels (classifying input coverage across rich documentation/code, partial sources, or tacit-only examination) and artifact verdicts (`BASELINE READY`, `PARTIAL`, `BLOCKED` in `en-US`; `BASE PRONTA`, `PARCIAL`, `BLOQUEADO` in `pt-BR`) are added to `requirements-rigor`, `CONTEXT.md`, the workflow `TEMPLATE.md` section-heading table, the workflow final notice, and the mechanical grader language table.
- **Three-input support in `/bootstrap-context`:** Step 1 inspects provided paths, workspace reference documents, existing `CONTEXT.md` and `product-overview.md` (for incremental runs), and in `with-code` mode dispatches a read-only subagent to map implemented domain entities, roles, integrations, and configured limits. When no documents or code exist, triage enters tacit-examination mode rather than failing, opening round 1 with structured baseline questions for the Product Owner.
- **Consolidated chat-mode memory handoff across all examination prompts:** `build-prompts` adapts glossary, ADR, and product-overview write instructions across all examination flows (`bootstrap-context`, `refine-story`, `requirements-discovery`, `qa-plan`). During rounds, resolved terms are noted briefly without dumping file blocks mid-examination. At synthesis, whenever the session added or flagged glossary terms, recorded an ADR, or changed product-overview facts, the response appends a dedicated Knowledge Base / Memory Updates delivery containing copy-ready blocks: full file replacement when creating from scratch or when the complete prior file was pasted inline in the conversation, and an explicit append/delta block when prior context came from platform memory where unseen entries could exist, paired with a reminder in the final report step to update the platform's memory or knowledge files before the next session.

## Testing Decisions

Good tests in this package verify observable contract behavior at existing mechanical and evaluation seams rather than internal prose phrasing:

- **Package validator and prompt builder seam (`validate-skills` and `build-prompts --check`):** verifies frontmatter and `openai.yaml` alignment for `bootstrap-context`, manifest and router registration (`plugin.json`, `README.md`, `which-flow`), zero em-dashes or en-dashes across all markdown and trigger files (including the Getting Started guides), live adaptation rules with zero unadapted workspace/tool references across all generated prompts (including `prompts/bootstrap-context.md`), and workspace configuration template invariants.
- **Artifact grader and glossary diff seam (`grade-output` and `diff-glossary`):** extends `grade-output` with `--skill bootstrap-context` in both `en-US` and `pt-BR` to verify triage label, verdict vocabulary, required product-overview sections in the configured language, rigor marker language consistency, recipient assignment on open questions backing `[TO CONFIRM]` markers, provenance citations on baseline claims, and final notice presence. Committed regression fixtures (`bootstrap-context-en-US` and `bootstrap-context-pt-BR`) are graded automatically by `validate-skills` with check counts recorded in `harness.md`, while `diff-glossary` continues to guard `CONTEXT.md` updates against silent rewrites or duplicates.
- **Evaluation suite seam (`evals/bootstrap-context.json` and chat-prompt assertions):** follows the existing `evals/*.json` prior art (`refine-story.json`, `requirements-discovery.json`) with cases covering `without-code` brownfield documentation in `en-US` and `pt-BR` (conflicting synonyms and unconfirmed legacy rules), `with-code` inspection over `code-workspace`, tacit-only cold start, and standalone chat-prompt execution verifying round-1 examination discipline and synthesis memory-update rules.

## Out of Scope

- Automated connectors or MCP integrations pulling pages directly from external wikis or trackers (Confluence, SharePoint, Notion, Jira, Azure DevOps APIs); users export or copy reference files into workspace documentation folders or paste them in chat.
- Automatic background synchronization into proprietary chat platform memory APIs (Claude Projects, OpenAI GPTs, Gemini Gems, Copilot Studio), which expose no write tool to in-chat prompts.
- Modifying the two model-invoked primitives' trigger eval sets unless their frontmatter `description` changes.

## Further Notes

- Re-running `/bootstrap-context` on a workspace that already has `CONTEXT.md` and `docs/product-overview.md` acts as an incremental curation pass: existing glossary definitions remain governed by the `socratic-examination` non-widening challenge rule so new legacy module docs cannot silently redefine terms established in prior stories.
