# Spec: the evaluation layer cannot answer whether the package works

Status: ready-for-agent
Origin: 2026-10-25 (commit 81547f6)

## Problem statement

The package is measured, and the measurements do not reach the claim it is built on. Three holes, in order of how much each one changes what we know.

Every eval case stops at the first examination round, because no Product Owner answers. The claim the package exists for, that rounds converge until the decision frontier empties and produce a User Story with a readiness verdict and testable criteria, has never been run end to end. What is measured today is how an interview opens.

Each case runs once. Repeat runs during the sessions recorded in ADR 0005 showed the same behavior landing at 0 of 5 and 4 of 4 depending on the language, so a single sample cannot separate a fix from variance, and a suite of single samples will report a lucky run as a fixed defect.

There is no baseline. No case has ever been run without the skills, so there is no evidence the package beats a competent model working from the fixture alone, which is the first question anyone evaluating adoption asks.

Two coverage gaps sit beside those holes. Mode `com-codigo`, where the agent inspects product code before asking, is half of what ADR 0001 promises and has zero cases. And `prompts/`, the chat version of every workflow, is generated by roughly seventy adaptation rules and never executed by an eval, so a drift in those rules ships a broken prompt with nothing to catch it.

## Solution

Reach the claim, then make the numbers mean something, then close the two coverage gaps.

A scripted Product Owner lets a session run to synthesis, so the grader can read the published artifact it was built for. Repeat runs with a pass-rate threshold replace binary single samples. A recorded baseline without the skills gives the comparison. A toy product repository gives `com-codigo` something to inspect. Two cases run against the generated prompts instead of the skills.

## User stories

1. As a maintainer, I want an eval case to run the examination to the end, so that the verdict and the Gherkin criteria the package promises are measured rather than assumed.
2. As a maintainer, I want each case measured over several runs against a threshold, so that I can tell a fix from a lucky run.
3. As a maintainer, I want the same cases run without the skills, so that I can say what the package adds.
4. As a maintainer, I want a case in `com-codigo` mode, so that the half of the package that reads code is covered.
5. As a maintainer, I want the generated chat prompts exercised, so that a drift in the adaptation rules fails a check instead of reaching a user.
6. As a maintainer, I want the triggering of the two model-invoked primitives measured, so that the rigor layer is known to load when it should.

## Seams

The existing ones, and no new ones. `scripts/grade-output.mjs` is the mechanical seam over a published artifact, `evals/*.json` is the assertion seam over a response, and `evals/fixtures/` is where inputs live. A scripted Product Owner is a fixture, not a new mechanism; a threshold is a convention in `evals/README.md` and a field in the grading summary, not a new runner.
